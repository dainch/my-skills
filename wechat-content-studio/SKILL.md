# wechat-content-studio

## 核心原则

- **公众号文章首选叙事化展开**：默认按 `references/editorial-rules.md` 第 0 节的四段式骨架写作（现场冲突 → 双方立场 → 错位点 → 判断与边界），用具体场景、角色、数字、代价开篇，再进推导。只有用户明确要求“纯手册体 / 纯清单体 / 只要提纲”时才跳过。叙事不得替代推导，技术数值必须可追溯并标注量级示例。
- 先交付接近可直接发布版本；只有用户明确要求“先看草稿/提纲”时，才停在中间态。
- 围绕同一个核心观点同时设计文章和视频，但“同题协同”不等于在公开成稿里默认写导流跳转动作。
- 专业准确性优先于流量技巧，但标题、钩子、关键词和封面必须具备传播能力。
- 公众号与视频号内容默认遵守“推荐运营规范 / 不良信息”收口：宁可降低一点刺激感，也不写夸张标题、热点蹭炒、事故消费、旧闻伪装新闻和诱导关注。
- 用户要求连续生产时，正常路径自动推进到 `status: ready`；不得自动改为 `published`，也不得调用正式发布接口。
- 网络搜索结果默认是 `candidate`。未打开原文、未交叉核验或未经用户确认时，不得将其当作确定性事实或自动摄取到 Wiki。
- 微信公众号文章生成后默认一并生成主封面图片，主封面固定按 **2.35:1**；不得只给封面文案替代封面成品。
- 能直接进入正文或脚本的内容，直接写进成品；不能进入最终成品且没有长期复用价值的中间资产，不单独建永久文件。
- 不把 Mermaid 直接留在公众号正文；需要图解时，改用简洁表格、文字结构、真实图片，或导出后的静态图。

## 开工前必做

1. 读取 `references/account-profile.md` 与 `references/engineering-project-context.md`，除非用户提供了更具体的账号定位、项目类型、受众或禁区。
2. 按任务类型读取一个投喂模板：公众号文章读 `references/prompt-article.md`；视频号视频读 `references/prompt-video.md`；图文联动或类型不明读 `references/prompt-linked.md`。
3. 如任务需要完整流程、质量底线或长期协作口径，读取 `references/full-workflow.md`。
4. 需要详细交付清单时，读取 `references/deliverables.md`；需要文件落地规则时，读取 `references/output-package.md`。
5. 发布前必须读取 `references/publish-gate.md` 与 `references/recommendation-compliance.md`，逐项检查硬门禁与改稿动作。
6. 如任务承接既有主题，先读取同系列的 `600-Output/01-WeChat/` 相关成稿、脚本或视频工程，保持账号口径一致。
7. 如内容需要事实支撑，回到 Wiki 或现有素材查证；不要把经验判断写成已验证事实。
8. 自动选题或资料发现任务读取 `references/research-pipeline.md`；需要公网检索时使用 `agent-reach`，并以真实业务调用结果判断后端是否可用。
9. 连续生产读取 `references/continuous-workflow.md`；自动审稿读取 `references/review-rubric.md`；生成待发布包读取 `references/publish-interface.md`。

## 任务分流

先把任务归入以下三类之一：

- **公众号文章**：重点是深度解释、搜索承接、收藏价值；默认生成文章和主封面。
- **视频号视频**：重点是前 3 秒钩子、单一核心判断、字幕关键词和完播节奏。
- **图文联动**：重点是同一份素材同时产出文章 + 1 到 3 条视频，并保持主题协同，不默认在公开内容中互相跳转。

若用户没有明确指定，按素材密度判断：

- 素材逻辑完整、证据充足、适合展开解释 → 先做文章，再拆视频。
- 素材冲突强、结论清晰、适合快传播 → 先做视频，再反推文章结构。
- 用户强调“系列化”“涨粉 + 建立专业形象” → 直接按图文联动处理；默认做选题协同，不默认做公开导流。

## 统一工作流

### 0. 选题与运行模式

用户已给主题时沿用主题；用户要求自动选题时，按 `references/research-pipeline.md` 生成候选并评分。选择证据可满足且得分最高的主题，不得为保持自动化而选择证据不足或高风险不可控的主题。

用户要求“连续完成”时使用 `continuous`；否则按 `direct`。状态和暂停条件以 `references/continuous-workflow.md` 为准。

### 1. 素材诊断与研究

明确并写清：主题、受众、发布目标、账号定位、项目类型、核心观点、专业依据、公开边界、禁区、搜索意图、证据缺口、是否涉及时事/公共政策/社会事件/灾害事故/医疗/金融/法律等高风险领域，以及当前素材更适合文章、视频还是联动。

先做 Brain-First 查询，再按证据缺口调用公网检索并建立来源账本。搜索摘要只作为线索；关键事实无法追溯时进入 `needs_material` 或 `needs_source_confirmation`，不要用模糊结论硬凑成稿。

### 2. 增长设计

至少完成以下设计动作：标题矩阵、主关键词与长尾词、前 3 秒钩子、公众号主封面、必要图表/清单、同主题内容协同、下一篇/下一条预告。

**公众号文章额外必做：叙事骨架设计。** 在写正文前，先用一句话写下四项内容，缺项不得进入写作：

1. **现场冲突**：谁遇上了什么事，代价是什么（含至少一个具体数字）。
2. **双方立场**：甲方的合理性一句，乙方的合理性一句。
3. **错位点**：两边其实在谈两个不同的东西，具体是哪两个。
4. **判断与边界**：本文最终给出的方法，以及它在哪些情况下不成立。

四项写不出来，说明选题还没想清楚，应回到素材诊断，而不是直接写。详细规范见 `references/editorial-rules.md` 第 0 节。

### 3. 成品制作

- **文章**：默认交付标题备选、摘要、正文、FAQ、互动引导、公众号主封面图片、必要图文建议。
- **视频**：默认交付标题、封面标题、口播脚本、字幕稿、发布文案；评论区置顶文案仅在用户明确要求时才生成。
- **联动**：默认交付文章 + 主封面 + 视频脚本 + 系列建议；公开成稿中不默认加入双向导流语句。

如用户没有要求先看提纲，直接输出接近可发布版本；不要把大量解释性备注、占位说明或内部工作痕迹留在主稿里。

创建 Output Markdown 时使用 `status: draft`；进入校审时改为 `reviewing`。只有全部硬门禁和发布包校验通过后才能改为 `ready`。

### 3.1 公众号主封面生成

生成公众号文章后，默认继续完成主封面生成，不等待用户再次提出：

1. 提炼封面主标题、副标题和主视觉关键词，确保与正文核心判断一致。
2. 优先用 `scripts/create_wechat_cover.py` 生成或制作主封面；默认尺寸 `2350 × 1000` PNG，比例 **2.35:1**。
3. 有 AI 主视觉时，采用“AI 生成无字背景 + 本地叠加中文标题”的两阶段流程，避免中文标题由图像模型直接生成导致字形不稳。
4. 最终说明封面文件路径、像素尺寸和宽高比；未验证尺寸前，不得声明封面已完成。
5. 只有用户明确说“不要封面/只要文字稿”时，才跳过图片生成；若环境确实无法生成图片，必须明确说明阻塞原因并给出可执行封面提示词，不能包装成已完成。

脚本示例：

```bash
python .agents/skills/wechat-content-studio/scripts/create_wechat_cover.py --title "主标题" --subtitle "副标题" --output "Attachments/主题-公众号封面-YYMMDD.png"
```

### 4. 图文联动编排

当同一份素材要同时做文章和视频时，遵守以下顺序：

1. 先抽出一个统一核心判断。
2. 用文章承接“为什么、边界、对比、误区、速查表”。
3. 用视频承接“钩子、一个判断、一个对比、一个结论”。
4. 保证文章和视频使用同一套核心关键词，但不要逐句照搬。
5. 如用户明确要求做平台内协同提示，只保留不离开当前页的弱提示；未确认前，不在公开成稿里预留互导句、跳转提示或二维码；固定“投稿邮箱 / 小编微信”按账号页脚口径处理。

### 5. 发布前校审

按以下顺序执行，任一步失败都保持 `reviewing` 并说明缺口：

1. 按 `references/review-rubric.md` 做六项自动审稿，按 `references/publish-gate.md` 与 `references/recommendation-compliance.md` 收口。
2. 运行 `python -X utf8 System/scripts/output_guard.py --dir <正文路径> --strict`，校验 Output frontmatter。
3. 运行 `python -X utf8 .agents/skills/wechat-content-studio/scripts/validate_wechat_article.py <正文路径>`，消除全部正文硬错误。
4. 对脚本报告的专业数字或行动阈值逐条填写 `claim_evidence`，生成 `schema_version: 2` 发布清单并运行 `scripts/validate_publish_manifest.py`。只有清单校验退出码为 `0` 才能改为 `ready`。

### 6. 待发布交付

按 `references/publish-interface.md` 生成正文、封面、校审结果和发布清单。默认止于 `status: ready`；不保存凭据，不推送草稿箱，不执行正式发布。`published` 只能由用户确认实际发布后设置。

## 文件落地规则

- 公众号文章、视频脚本、联动文稿统一优先落在 `600-Output/01-WeChat/`。
- 新建 Markdown 时遵守 Output 最小规范：`output_profile`、`source_refs`，必要时加 `status`。
- Output 的 `status` 可用于 `draft`、`reviewing`、`ready`、`published`，但不得复用 Wiki 生命周期状态。
- 标准交付包按 `references/output-package.md` 执行。
- 与正文无关、又没有长期复用价值的临时文件不要永久保留。

## 默认完成度

除非用户明确要求“只给提纲”“只给提示词”“只做脚本”，否则默认目标是：文章接近公众号成稿，视频接近可录制或渲染，联动能在主题层面接入后续系列，但不默认包含二维码、外链、评论区引流或跨页面跳转；固定“投稿邮箱 / 小编微信”可作为账号页脚信息保留。始终优先降低用户二次整理成本。
