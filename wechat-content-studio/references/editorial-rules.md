# 编辑规则与经验固化

## 0. 叙事优先（公众号文章首选方案）

> 本小节为公众号文章的第一优先写作口径。除非用户明确要求“纯技术手册体 / 纯清单体 / 只要提纲”，否则按本节执行。

### 0.1 为什么叙事优先

工程类公众号的读者大多在通勤、睡前、工位上刷手机，**先被场景留住，才愿意看推导**。同样的技术结论，写成“定义—公式—结论”没人往下翻，写成“现场发生了什么—双方各自怎么想—到底卡在哪—所以该怎么算”，完读率完全不同。

**判断标准**：把文章前 200 字单独拿出来给人看，如果他不能复述出“谁遇上了什么事、卡在什么地方”，就是不达标。

### 0.2 默认结构：四段式叙事骨架

| 段落 | 作用 | 写作要求 |
| :--- | :--- | :--- |
| **① 现场冲突** | 用具体场景开局 | 有人、有事、有数字、有代价。第一段就出现“谁遇到了什么麻烦” |
| **② 双方立场** | 呈现对立，先不给答案 | 甲方为什么这么说，乙方为什么那么说。**两边都要写出合理性** |
| **③ 错位点** | 揭示矛盾真正的根源 | 不是“谁不懂”，而是“两个东西被混为一谈了” |
| **④ 判断与边界** | 给方法、给适用条件 | 推导 + 表格 + 不适用情形，收口时回归场景 |

### 0.3 开篇场景化的硬要求

**必须包含以下至少三项**，缺项视为不合格开篇：

- **具体数字**：实测值 vs 设计值、停工天数、损失金额、构件尺寸、荷载量级。
- **具体角色**：质检站、项目部、设计院、监理、总包、分包——不是抽象的“施工单位”。
- **具体代价**：停工、返工、罚款、工期、设备倾覆、渗漏水。
- **具体动作**：不签字、拒绝验收、拍桌子、连夜算账、打报告。

**反面写法（禁止）**：

> “地下通道项目，坑底土层遇水软化，质检站现场检测承载力不够，项目部觉得冤……”

这只是概述，没有现场。读者不知道事儿有多大、是谁在争。

**正面写法**：

> “某市政下穿通道，基坑刚开挖到底，坑底土被雨水泡了两天。质检站进场做平板载荷试验，实测 110 kPa，图纸要求 f_ak ≥ 150 kPa。不合格，不签字。项目部满腹委屈……停工一天，人机都在那儿耗着。谁之过？”

### 0.4 叙事与专业性的三条纪律

1. **场景可以是复合的，数据不能是编的**：允许把一个项目的场景与另一个项目的数值组合成“典型情境”，但**所有技术数值必须可追溯**，且在文中标注“量级示例 / 仅示意 / 具体项目须代入计算”。虚构现场不标注，等同于造假。
2. **叙事不能替代推导**：场景只负责拉住读者，结论仍必须由公式、对照表、适用边界撑住。**“故事 + 无推导”是营销稿，不是技术稿。**
3. **不消费事故、不假装亲历**：涉及伤亡事故时，写风险链条与管理启示，不做细节渲染；引用他人案例须写明来源与时间，不得写成“我亲眼见过”。

### 0.5 叙事化的常见手法（按题材选）

| 手法 | 适用题材 | 示例 |
| :--- | :--- | :--- |
| **现场冲突开场** | 甲乙争议、验收扯皮、责任划分 | 质检站不签字，项目部说没问题 |
| **反差对照** | 规范要求 vs 现场实际 | 图纸 150，实测 110 |
| **反常识提问** | 经验误区、以讹传讹 | “坑底都没压它，为什么还要验承载力？” |
| **一句台词切入** | 沟通话术、评审现场 | “请把承载力要求降一点” vs “请按工况复核” |
| **代价倒推** | 事故复盘、风险提醒 | 停工一天几十万，问题出在哪一步 |

### 0.6 叙事段落的技术衔接

故事讲完必须**明确转场**，不能让读者停在情绪里：

- 转场句式：“这个分歧我见过不止一次……**真正的问题在于**：”
- 转场后立即给出**可检验的判断**（一行公式、一句定义、一张对照表），把叙事锚回专业。
- 每个大章结尾最好有一句**收口金句**，便于读者截图转发；金句必须与正文结论一致，不得为了押韵夸大。

### 0.7 金句与加粗的使用边界

- 全文金句（引用块形式）建议 **3~6 处**，多了会稀释。
- 金句只写**已被正文论证过的判断**，不写悬念、不写口号、不写“聪明人都懂”。
- 加粗用于**结论和转折**，不用于整段加粗；一段里加粗超过 2 处即视为滥用。

## 1. 正文与中间资产

- 能直接进入正文的图片、表格和完整信息，直接进入正文。
- 不能进入最终正文、又没有长期复用价值的内容，不单独建永久文件保存。
- 不把“发布辅助资产”当成默认中转站；只有真正长期复用的模板、清单、规范才值得单独保存。

## 2. 图片与图解

- 历史文章已有外链图片时，优先直接复用链接，不先下载本地。
- 微信公众号文章生成后默认一并生成主封面图片；主封面比例固定为 **2.35:1**，推荐 `2350 × 1000` PNG。若用户未特别说明，不使用 21:9、1:1 或其他平台比例代替主封面。
- 公众号正文优先使用真实图片、普通表格、短清单、简洁说明。
- Mermaid 只适合笔记整理，不适合直接留在公众号正文源码里。
- 若确实需要图解，优先准备静态图片思路，而不是把 Mermaid 代码塞给读者。

- 封面生成优先采用“AI 生成无字背景 + 本地叠加中文标题”的两阶段流程；最终必须核对文件路径、像素尺寸和宽高比。

## 3. 默认完成度

- 用户没有要求草稿时，默认交付接近可直接发布版本。
- 文章要去掉草稿感、占位感和解释型工作痕迹。
- 视频不能只是“单画面 + 导出 mp4”；至少要有场景推进、信息节奏和音轨，才算可交付。

## 4. 图文联动

- 从长文拆视频时，优先压缩成“钩子 - 判断 - 对比 - 结论”四段式。
- 不照搬全文结构，不试图把整篇文章压缩成一条视频。
- 图文同源时，文章负责深度，视频负责快速表达；保持主题协同，不默认加入互导语句。

## 5. 专业与增长平衡

- 不把猜测写成结论。
- 没有后台数据时，不把“可能高关注”写成已验证事实。
- 标题可以有吸引力，但不能和正文结论脱节。
- 不把旧闻包装成新事，不消费事故灾难，不用“防失联先关注”“后面有大料”这类诱导关注写法。
- 如使用 AI 演绎图、示意图或非实拍画面，且可能被误认成真实现场，应显式标注。

## 6. 发布门禁

- 发布前硬门禁以 `publish-gate.md` 为准；任一硬门禁不满足时，停止并说明缺口，不得包装成已完成。
