# 自动审稿规则

成稿进入 `reviewing` 后依次执行以下检查。任一硬门禁失败时保持 `reviewing`，输出问题和修复动作；全部通过后才允许改为 `ready`。

## 1. 事实与来源

- 每个关键判断能映射到 Wiki、Sources、用户确认材料或已交叉验证的第一方来源。
- 搜索摘要、公众号转载和营销案例未被当作权威事实。
- 规范、政策、参数、日期和产品能力已核对版本与适用时间。
- 正文中的专业数字或行动阈值逐条写入发布清单 `claim_evidence`，并映射到顶层 `source_refs`。

## 2. 专业与边界

- 说明适用工程条件和不适用场景。
- 不把单个案例、经验判断或相关性外推为通用因果结论。
- 技术参数、项目名称、单位、人员、坐标和原始监测数据已脱敏或获确认。

## 3. 原创与版权

- 未复刻同题文章的段落、标题组合或独特表达。
- 外部图片、图纸、音乐和视频具有可用授权，或仅提供替代制作建议。
- AI 生成或演绎画面可能被误认成现场时已标注。

## 4. 传播与账号口径

- 标题、摘要、首屏、正文、封面和视频钩子表达同一核心判断。
- 主关键词自然出现在标题、首屏和相关小标题中。
- 文章完整自洽，不依赖二维码、私信、回复关键词或跨页跳转获取正文。
- 文风符合账号画像，删除空泛套话、重复总结和内部工作备注。

### 4.1 叙事化检查（公众号文章必查）

按 `editorial-rules.md` 第 0 节逐项核对：

- **开篇**：前 3 段内出现具体场景，且同时具备「角色 + 数字 + 代价」中的至少两项。只有概述、没有现场的，判 fail。
- **双方立场**：争议类选题必须写出甲方、乙方各自的合理性；只写一方正确的，判 fail。
- **转场**：故事之后有明确转场句，并把读者锚回公式、定义或对照表；故事讲完直接进结论的，判 fail。
- **推导**：场景不替代技术论证，核心结论有公式、表格或适用边界支撑；只有故事没有推导的，判 fail。
- **数值可追溯**：所有技术数字有来源或明确标注「量级示例 / 仅示意 / 须代入计算」；未标注的虚构数值判 fail。
- **金句**：引用块 3~6 处，且只写正文已论证的判断；出现口号式、悬念式、夸大式金句的，判 fail。
- **加粗**：单段加粗不超过 2 处，不整段加粗。

## 5. 推荐合规

读取 `recommendation-compliance.md`，检查夸张标题、假时效、热点蹭炒、事故消费、诱导关注、离页导流和仿官方口吻。任何一票否决项必须改稿。

## 6. 产物完整性

- Output frontmatter 符合仓库规范，`source_refs` 有效。
- 主封面文件存在，尺寸为 `2350 x 1000`，比例为 `2.35:1`。
- 正文无占位符，图表和图片说明可执行。
- 正文通过 `scripts/validate_wechat_article.py`，无导流、跨内容提示、公开 Wiki-link、外链或一级标题等硬错误；固定投稿邮箱和小编微信不视为硬错误。
- 发布清单通过 `scripts/validate_publish_manifest.py`。

校审报告固定输出六项：`facts`、`source_traceability`、`sensitivity`、`compliance`、`title_body_cover`、`output_schema`；值只能为 `pass` 或 `fail`。
